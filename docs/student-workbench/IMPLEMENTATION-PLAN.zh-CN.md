# dsh-widget-board 详细实施计划

## 1. 目标与交付

让原插件具备规则整齐的可选排列、容易发现的看板管理、页面内自定义卡片编辑，以及带学校特色和学位身份预设的校园综合卡。保留原作者的视觉语言和安全架构。

本次只交付方案、本地审阅工具与 fork。本文件是以后 DS 实施的依据，不能当作功能已完成的证明。用户确认记录见 [决策表](DECISIONS.md)，事实依据见 [源码核查](UPSTREAM-AUDIT.md)。

## 2. 为什么这样拆分

原插件已经能删除看板、配置简单 props、导入组件包和通过 Agent 创建组件。当前需要补足的是页面入口、复杂内容编辑和新的排列方式。沿用既有存储、组件格式和 iframe 渲染，能缩小回归范围。

四项产品贡献分别建立功能分支：看板管理、整齐排列、自定义编辑器、校园卡片。编辑器内部的表单、源码、媒体按小任务交付；校园内部的展示、文件交换、提醒分别交付。分支用于审查主题，任务用于控制单次修改范围，两者不必一一相等。

## 3. 用户操作路径

### 3.1 整理看板

进入看板 → 加号菜单 → 排列方式 → 整齐行列。第一次切换以当前画面的阅读顺序生成顺序，所有卡片按行排列；同排等高。切回自由布局恢复此前位置。旧看板升级时维持原貌。

### 3.2 管理标签

悬停或聚焦标签显示更多按钮，右键也打开同一个菜单。选择重命名，输入后保存；选择删除，确认看板名与卡片数量后删除。最后一块删除后仍有一块新空看板。

### 3.3 创建自定义卡片

加号菜单或组件库 → 创建卡片 → 选择模板 → 编辑内容 → 查看真实沙箱预览 → 添加到当前看板。普通编辑只改当前实例。修改共享源码时先明确“仅当前卡片另存”或“更新该类型所有实例”。

### 3.4 创建校园卡

创建卡片 → 校园综合卡 → 选择通用、四校或自定义学校 → 选择本科、硕士、博士 → 预览 → 添加。以后在卡片内新增事项，或从管理界面导入 CSV/ICS。默认没有虚构的正式日期。

## 6. 稳定性要求

1. 所有持久化由宿主完成，客户端不自行把正式状态留在 localStorage。
2. 移动、缩放和换行不移动 iframe 的父节点，不重建正常运行的组件。
3. 旧看板、旧组件、旧提供方继续工作；未来格式明确报错。
4. 界面失败有可见说明，保留输入；不吞错、不伪造成功。
5. 新权限必须声明并由既有审批路径处理；预览不取得正式授权。
6. 新媒体只允许读取当前实例获准关联的资源；前端传来的资源归属不可信。
7. 卡片数据、请求体、桥消息、文件包分别校验额度，不能混为一个限制。
8. 学校预设只包含名称、核实后的官方入口、原创图案与局部配色；不推断真实教务安排。

## 7. 视觉要求

保持宿主字体、24px 卡片圆角、现有间距和字号体系、点阵背景、轻边框及现有阴影。学校色只影响校园卡片内部视觉，操作控件和状态色仍读取原语义令牌。原生主题及 dsh-claude-style 的浅深色都需要核对。

每次视觉修改提供同视口原版对照、修改后浅深色截图以及窄/矮尺寸图。没有实际查看图片不能把视觉验收标为通过。[视觉规格](VISUAL-SPEC.md) 定义具体核对项。

## 8. 验证策略

从行为层检查用户能看到的结果：同排边缘一致、菜单能点击、刷新后仍在、失败后未丢输入、导入重复项能够解释。使用真实的文件往返和宿主隔离环境，不靠 mock 替代集成验收。

阶段可以运行有针对性的单元检查；每个功能分支进入可交付状态及 T08 集成时完整运行原项目 `npm run verify`。改变演示页的功能另做 demo 检查。缺少依赖、宿主或浏览器时保留“未执行”，不降低检查要求。

最终验收以 [验收矩阵](ACCEPTANCE-MATRIX.md) 为准。局部 guard 是额外审阅辅助，不替代原项目 verify。

## 9. 风险及已选处理

| 风险 | 已选处理 |
|---|---|
| 新模式破坏原布局 | 两种偏好分别保存，旧数据默认 free |
| 原 2rem 纵向吸附使间距变大 | aligned 使用独立纯模型，不经过自由位置吸附 |
| 共享组件源码误改多张卡片 | 默认另存为新用户类型，显式显示全部实例影响 |
| 图片超过状态或桥上限 | 资源存盘、实例引用、能力分块读取 |
| 编辑后覆盖其他窗口的新内容 | 内容哈希或修订号冲突返回 409 |
| ICS 时区和重复规则误解 | 使用成熟库；不能解释的项目进入错误预览 |
| AI 一次改太多或跳过检查 | 九个任务、文件范围、证据绑定与提交 hook |
| 推错上游、主分支或覆盖历史 | 固定fork目标＋上游push地址禁用＋pre-push检查引用及快进关系 |

## 10. 完成后的交付

代码、测试、迁移记录、双语使用说明、原创素材来源表、真实截图、验收证据和分项 PR 正文。当前 Issue 草稿留在本地，未来提交 PR 不以先创建 Issue 为前提。

用户仍需查看浅深色视觉结果；这项核对不阻止DS继续完成其余工作。阶段commit/push到自己的fork随时允许，未验证的版本明确标记。全部完成后交付可审阅材料，用户再明确授权上游PR等投稿动作。
